# 데브로그 글 첨삭

대상은 사용자가 지정한 글입니다. 지정하지 않았으면 IDE에 열린 `src/content/devlog/` 파일을 쓰고, 그것도 없으면 어떤 글인지 물어봅니다. 글 하나를 처음부터 끝까지 읽은 뒤 아래 순서대로 작업합니다.

## 공통 원칙

- 글쓴이의 사실, 주장, 경험, 말투를 지킵니다. 글에 없는 사실, 수치, 일화를 지어내지 않습니다.
- 문단과 섹션의 순서는 필요할 때만 바꿉니다.
- 다음은 아래 단계에서 정한 경우가 아니면 고치지 않습니다: 코드 블록과 인라인 코드 안의 내용, URL, `import` 줄, 컴포넌트 이름과 prop 이름, `tags`, 고유명사와 디자인 토큰 이름(Night Desk, Lamp Gold 등).
- 날짜 필드와 파일 이름은 7단계 규칙으로만 바꿉니다.
- `templates/devlog-post.mdx`에서 시작한 글은 첨삭할 때 `{/* */}` 안내 주석, 쓰지 않는 `import`, 내용이 없는 `## 소제목`을 지웁니다.

## 1. PROMPT 지시문 처리

`PROMPT(...)`는 글쓴이가 AI에게 남긴 지시문입니다. 괄호 안 문장을 그대로 싣지 않고, 지시를 수행한 결과로 `PROMPT(...)` 전체를 바꿉니다. 본문과 frontmatter(`title`, `description`)를 모두 찾습니다. 코드 블록과 인라인 코드 안의 `PROMPT(...)`는 예시이므로 건드리지 않습니다.

- 괄호 안에 괄호가 있으면 짝이 맞는 닫는 괄호까지가 지시문입니다.
- 지시문이 짧거나 문장이 끝나지 않았으면 놓인 자리로 뜻을 판단합니다. 예를 들어 `description: 'PROMPT(글 내용을 보고 )'`는 글 내용을 보고 설명을 쓰라는 뜻입니다.
- 결과는 글의 문맥에 이어지게 쓰고, 이 스킬의 문체 규칙을 따릅니다. `description`은 글 목록과 검색 결과에 보이는 한두 문장으로 씁니다.
- 수행하려면 글에 없는 사실이 필요하면 지어내지 말고 `PROMPT(...)`를 그대로 둔 뒤 무엇이 필요한지 알려 줍니다.

## 2. 첨삭

- 맞춤법, 띄어쓰기, 오타를 고칩니다.
- 어색한 표현, 번역투, 끊기거나 비문인 문장을 자연스럽게 고칩니다.
- 같은 단어나 표현의 반복을 줄이고, 뜻이 겹치는 문장은 하나로 합칩니다. 강조나 리듬을 위해 일부러 반복한 표현은 둡니다.

## 3. 해요체로 통일

본문 문장, Callout 안의 문장, 문장으로 끝나는 `title`, `description`, 제목을 해요체(`-해요`, `-이에요`, `-예요`, `-어요`)로 맞춥니다. `-습니다`, `-한다`, `-함`이 섞이지 않게 합니다.

- 같은 어미가 연달아 나오면 문장을 합치거나 어순을 바꿔 단조롭지 않게 합니다.
- 말끝을 지나치게 귀엽게 만들지 않고, 글쓴이의 차분한 말투를 유지합니다.
- 다음은 그대로 둡니다: 명사로 끝나는 제목과 목록 항목(`앞으로 쓸 이야기`), 인용문, AI에게 전달한 프롬프트 원문, 코드.

## 4. 소제목 추가

글을 읽고 주제가 바뀌는 지점이나 하나의 소주제로 묶이는 문단들 앞에 `## ` 제목을 넣습니다.

- 두 문단 이상을 묶을 수 있을 때만 넣고, 문단마다 제목을 달지 않습니다. 글 첫머리의 인사나 도입 문단에는 넣지 않습니다.
- 제목은 그 구간의 내용을 요약한 짧은 명사구로 쓰고, 글에 없는 내용을 담지 않습니다.
- 글쓴이가 쓴 제목은 유지합니다. 제목 수준은 `##`(h2)를 쓰고, `#`은 쓰지 않습니다.

## 5. GitHub 저장소 상자

`https://github.com/소유자/저장소` 형태의 저장소 URL은 일반 링크 대신 `RepoCard`로 보여 줍니다. 코드 블록 안의 URL과 이미 `RepoCard`인 것은 제외합니다.

```mdx
import RepoCard from '../../components/RepoCard.astro';

<RepoCard url="https://github.com/jusiai-games/예시-저장소" description="저장소를 한 줄로 설명하는 문장이에요." />
```

- URL이나 링크만 있는 문단, 목록 항목은 `RepoCard`로 바꿉니다.
- 문장 안의 URL은 문장을 자연스럽게 고쳐 URL을 빼고, 그 문단 바로 아래에 `RepoCard`를 둡니다. 저장소 하나가 글에 여러 번 나오면 카드는 처음 한 번만 두고, 이후에는 저장소 이름만 씁니다.
- `description`은 글에 나온 내용으로 쓰고, 근거가 없으면 생략합니다. 저장소 내용을 추측하지 않습니다.
- `import`는 frontmatter 아래 다른 `import`와 함께 두고, 쓰이지 않게 된 `import`는 지웁니다.
- 프로필(`github.com/jusiai-games`), 파일, 이슈, PR 링크는 `RepoCard`가 받지 않으므로 일반 링크로 둡니다. URL 끝의 `/`와 `.git`은 있어도 됩니다.

## 6. 이미지

본문의 이미지는 HTML `<img>`나 Markdown `![]()` 대신 `PostImage`와 `ImageCollage`로 보여 줍니다. 코드 블록 안의 예시는 제외합니다. 이미지는 https://github.com/jusiai-games/blog-images-2026 저장소에 있습니다.

```mdx
import ImageCollage from '../../components/ImageCollage.astro';
import PostImage from '../../components/PostImage.astro';
import { IMAGE_URL_2026 } from '../../consts';

<PostImage src={`${IMAGE_URL_2026}/file.jpg`} alt="이미지 설명" caption="이미지 아래에 보일 설명" />

<ImageCollage
  images={[
    { src: `${IMAGE_URL_2026}/file1.jpg`, alt: '첫 번째 이미지 설명' },
    { src: `${IMAGE_URL_2026}/file2.jpg`, alt: '두 번째 이미지 설명' },
    { src: `${IMAGE_URL_2026}/file3.jpg`, alt: '세 번째 이미지 설명' },
  ]}
  caption="콜라주 아래에 보일 설명"
/>
```

- `src`에 `file.jpg`처럼 파일 이름이나 상대 경로만 있으면 앞에 `${IMAGE_URL_2026}/`을 붙입니다. `https://`나 `/`로 시작하는 주소는 그대로 쓰고 컴포넌트만 바꿉니다.
- `<div>` 같은 블록 하나에 이미지가 두 장 이상 있거나, 빈 줄 없이 이미지가 이어져 있으면 `ImageCollage`로 묶습니다. 레이아웃은 이미지 수에 맞춰 컴포넌트가 정합니다. 빈 줄로 나뉜 이미지와 블록 안의 이미지 한 장은 각각 `PostImage`로 씁니다.
- `ImageCollage`는 이미지를 칸에 맞춰 잘라서 보여 줍니다. 전체가 보여야 하는 스크린샷이나 도표로 보이면 그대로 묶되 보고할 때 알려 줍니다.
- `alt`는 이미 있으면 유지하고, 없으면 주변 글과 파일 이름으로 씁니다. 근거가 부족하면 이미지를 내려받아 직접 봅니다. 그래도 알 수 없으면 `alt=""`로 두고 알려 줍니다.
- `caption`은 글쓴이가 이미지 설명으로 쓴 문구가 있을 때만 씁니다. 없으면 생략합니다.
- `import`는 쓰는 것만 추가합니다.

## 7. 날짜와 파일 이름

첨삭을 마친 뒤 처리합니다. 오늘 날짜는 `date +%F`로 구합니다.

**새 글인지 판단:** `git cat-file -e HEAD:<경로>`가 실패하면 새 글, 성공하면 기존 글입니다. 스테이지만 되고 커밋되지 않은 파일도 새 글입니다. 커밋된 글이 `git status`에서 삭제로 나오고 대상 글과 같은 글로 보이면, 이름만 바뀐 기존 글일 수 있으니 바꾸지 말고 사용자에게 물어봅니다.

| 항목 | 새 글 | 기존 글 |
| --- | --- | --- |
| `updatedDate` | 오늘 | 오늘 |
| `pubDate` | 오늘 | 그대로 |
| 파일 이름의 날짜 | 오늘(다른 날짜가 있으면 교체) | 있으면 그대로, 없으면 `pubDate` 날짜를 앞에 추가 |
| 슬러그 | 필요하면 새로 지음 | 그대로 |

- 날짜 필드는 `'YYYY-MM-DD'` 형식으로 쓰고, `updatedDate`가 없으면 `pubDate` 아래에 추가합니다.
- 파일 이름은 `YYYY-MM-DD-{topic}.mdx`입니다. 확장자는 유지하고, `.md` 글에 `import`가 필요해지면 `.mdx`로 바꿉니다.
- 새 글의 슬러그는 파일 이름이 아니라 첨삭한 글 내용을 보고 판단합니다. 오타가 있거나, 내용과 맞지 않거나, 검색될 만한 주제어가 없으면 새로 짓습니다.
  - 글의 핵심 주제어를 담은 영어 소문자 kebab-case 3~6단어로 씁니다. 예: `solo-game-dev-ai-workflow`
  - `post`, `new`, `test`, `draft`처럼 뜻이 없는 단어와 날짜는 넣지 않습니다.
  - 다른 글과 슬러그가 겹치면 URL이 충돌하므로 다른 이름을 씁니다.
- 기존 글의 슬러그를 고치지 않는 이유는 공개된 URL이 바뀌기 때문입니다. 오타가 있으면 알려 주기만 합니다. 날짜 접두사는 URL에 들어가지 않으므로 추가해도 URL은 그대로입니다.
- 이름 변경은 Git이 추적 중인 파일이면 `git mv`, 아니면 `mv`로 합니다. 슬러그가 바뀌었다면 저장소에서 옛 슬러그를 검색해 링크도 고칩니다.

## 8. 확인과 보고

1. 글에 처리하지 않은 `PROMPT(`가 남았는지, `-습니다`, `-습니까`가 남았는지, 코드 블록 밖에 `<img`나 `![`, `{/*`가 남았는지 검색합니다.
2. `IMAGE_URL_2026` 이미지마다 `curl -sI`로 주소를 확인합니다. 빌드는 없는 이미지를 잡아 주지 않으므로, 200이 아니면 저장소에 파일이 없는 것으로 알려 줍니다.
3. `npm run build`를 실행해 오류와 경고가 없는지 확인합니다.
4. 커밋하지 않고, 다음을 짧게 알려 줍니다.
   - 바뀐 내용 요약과 `PROMPT`를 바꾼 결과
   - 바뀐 날짜와 파일 이름, 최종 URL
   - 추가한 소제목, 찾지 못한 이미지, 잘려도 되는지 확인할 이미지
   - 뜻이 바뀌었을 수 있어 글쓴이가 확인할 문장
   - 고치지 않은 문제: 기존 글의 슬러그 오타, 사실이 의심스러운 내용, 기존 글의 파일 이름 날짜와 `pubDate`가 다른 경우, 남겨 둔 `PROMPT`
